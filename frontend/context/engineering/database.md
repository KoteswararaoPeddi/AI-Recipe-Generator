# Database — Engineering Decisions (Prisma & Postgres)

> Notable database decisions, written to **teach** — Prisma is new here, so entries also carry a
> **Learned / Gotcha** line where it behaved non-obviously. Format: vocabulary (if needed) → ❌ naive vs
> ✅ our code → why → **where else you'd use it** → rule of thumb. See [README](./README.md).
> Schema: `backend/prisma/schema.prisma`.

## Schema & Data Modeling

### `cuid()` primary keys on every model
- **What:** Every model uses `@id @default(cuid())` rather than autoincrement int or uuid.
- **Where:** `schema.prisma` (all models).
- **Why:** Collision-resistant, URL-safe, non-sequential IDs that don't leak row counts and don't need DB round-trips to generate.
- **Learn**

  ````prisma
  // ❌ autoincrement int — sequential IDs leak scale ("/users/1042" tells attackers your user count)
  //    and are guessable (/orders/1043 might be someone else's)
  id Int @id @default(autoincrement())

  // ✅ cuid — collision-resistant, URL-safe, opaque, generated by the app (no DB round-trip to learn it)
  id String @id @default(cuid())   // e.g. "clr2x8k9a0001..." — reveals nothing, unguessable
  ````

  ID choice has security and scaling consequences. **Sequential ints** reveal how many rows you have and
  make adjacent records guessable (helps IDOR attacks). **cuid/uuid** are opaque and unguessable, and can
  be generated client/app-side so you know the ID before inserting. cuid is shorter/URL-friendlier than a
  raw uuid.

  **Where else you'd use it:** public-facing IDs (URLs, API responses), distributed systems (generate IDs
  without coordinating with the DB), anywhere you don't want to leak counts. Ints are fine for purely
  internal join tables where none of that matters.

  **Rule of thumb:** if an ID appears in a URL or API response, make it opaque and unguessable
  (cuid/uuid), not a sequential int. Never expose row counts through your IDs.

### Snake_case plural tables via `@@map`, PascalCase models in Prisma
- **What:** Models stay PascalCase singular (`User`, `PantryItem`); tables are `@@map`'d to snake_case plural (`users`, `pantry_items`).
- **Where:** `schema.prisma:78,92,110,140,156,173`.
- **Why:** Idiomatic Prisma model names in code + conventional SQL table names in the DB. *(Naming convention — no deeper lesson.)*

### User-centric model with cascade delete on every per-user row
- **What:** `User` is the hub; Preference, PantryItem, Recipe, MealPlanEntry, ShoppingItem all declare `onDelete: Cascade`. `MealPlanEntry.recipe` also cascades, so deleting a recipe wipes its plan entries.
- **Where:** `schema.prisma` lines 90,107,134,151,170 (+ 152 for recipe→entry); rule stated in the header comment.
- **Why:** Deleting a user (or recipe) cleans up all dependent rows atomically at the DB level — no orphan rows, no manual cascade code.
- **Learn**

  **Vocabulary:** a *foreign key* is a column pointing at another table's row (e.g. `Recipe.userId → User.id`).
  An *orphan* is a child row whose parent was deleted. *Cascade delete* = "when the parent goes, delete
  the children too."

  ````prisma
  // ✅ the relation declares what happens to children when the parent is deleted
  model Recipe {
    userId String
    user   User @relation(fields: [userId], references: [id], onDelete: Cascade)  // user gone → recipes gone
  }
  // Without onDelete: Cascade, deleting a user whose recipes exist ERRORS (FK violation) — or, if you
  // force it, leaves recipes pointing at a user that no longer exists (orphans).
  ````

  Letting the **database** enforce cleanup is more reliable than doing it in app code. With `onDelete:
  Cascade`, one `DELETE FROM users WHERE id = ...` transactionally removes the user and every dependent
  row — you can't forget a table, and there's no window where orphans exist. The alternative (manually
  deleting children in the right order in a service) is error-prone and easy to leave incomplete.

  **Where else you'd use it:** account deletion (GDPR "delete my data"), deleting a project and its
  tasks/comments, a post and its likes — any strict parent→children ownership. Use `onDelete: SetNull`
  instead when children should *survive* the parent (e.g. keep orders after a product is removed).

  **Rule of thumb:** model ownership in the schema. If children have no meaning without the parent,
  `onDelete: Cascade`. If they should outlive it, `SetNull`/`Restrict`. Let the DB enforce it, not app code.

### JSON columns for semi-structured recipe data
- **What:** `Recipe.ingredients / steps / nutrition / tips` are `Json` rather than normalized child tables.
- **Where:** `schema.prisma:126-129`.
- **Why:** These are always read/written as a whole recipe and never queried field-wise; JSON avoids a join-heavy schema for no query benefit.
- **Learned / Gotcha:** Prisma `Json` fields are opaque to the query engine — you can't index or filter *inside* them. Fine here because we never need to; wrong call if we had to search by ingredient.
- **Learn**

  ````prisma
  // ❌ fully normalized — correct, but 4 extra tables + joins for data you always load together anyway
  model Ingredient { id String @id, recipeId String, amount String, name String }  // …and Step, Tip, Nutrition

  // ✅ store the sub-structure as JSON on the recipe — one row, one read, no joins
  model Recipe {
    ingredients Json   // [{ amount, name }, …]  — always read/written with the whole recipe
    nutrition   Json   // { calories, protein, … }
  }
  ````

  Normalization (splitting data into related tables) is the default and usually right — but it's a means,
  not a religion. Here the sub-data is *only ever* accessed as part of its recipe and is *never* queried
  independently ("find recipes with >20g protein" isn't a feature), so normalizing into 4 child tables
  buys joins and complexity for zero query benefit. JSON keeps a recipe one row, one read. The **trade-off**:
  the DB can't index or filter inside JSON, so the moment you *do* need "search by ingredient," you'd
  normalize that part.

  **Where else you'd use JSON columns:** settings/preferences blobs, event payloads, API snapshots,
  flexible metadata — data read as a unit and not filtered on. **Normalize instead** when you need to
  query, index, or enforce constraints on the inner fields.

  **Rule of thumb:** normalize what you query; JSON what you only ever read/write as a whole. Ask "will I
  ever filter or join on a field inside this?" — if no, JSON is fine.

### Typed enums alongside parallel free-text/array fields
- **What:** Deliberate mix: `Recipe.diet` (enum) vs `dietTags String[]`; `Preference.dietaryRestrictions String[]` + `allergies String` (comma-separated). 5 enums: `Diet`, `Cuisine`, `Difficulty`, `MealSlot`, `RecipeSource`.
- **Where:** `schema.prisma:17-57,120,84-85`.
- **Why:** Enums give type safety on filterable fields; the string/array parallels hold free-form display data the enum can't express.
- **Learn**

  ````prisma
  diet     Diet        // enum: ONE canonical, filterable, type-safe value (Vegan | Vegetarian | …)
  dietTags String[]    // free-form display chips ("high-protein", "gluten-free") — open-ended, not filtered
  ````

  Enum vs free text is a real modeling decision. **Enums** are for a closed, known set you filter and
  branch on — the DB and TypeScript both enforce validity. **Strings/arrays** are for open-ended,
  display-only, or user-supplied values you don't want to keep migrating the enum for. Using both,
  deliberately, gives type safety where it matters and flexibility where it doesn't.

  **Where else you'd use it:** `status` (enum) vs `labels` (free tags); `role` (enum) vs `bio` (text);
  `paymentMethod` (enum) vs `notes`. Enum the thing you switch on; string the thing you just show.

  **Rule of thumb:** enum a **closed set you filter/branch on**; string/array an **open set you only
  display**. If you'd have to run a migration every time a new value appears, it probably shouldn't be an
  enum.

### Date-only columns and a nullable refresh-token field
- **What:** `PantryItem.expiryDate` and `MealPlanEntry.date` use `@db.Date` (no time); `User.hashedRefreshToken String?` where null = logged out.
- **Where:** `schema.prisma:102,146,68`.
- **Why:** Expiry/meal dates are calendar days, not timestamps; nullable token field doubles as the logout/invalidation signal.
- **Learn**

  ````prisma
  expiryDate         DateTime @db.Date   // stores 2026-07-04, not 2026-07-04T13:22:07Z — no TZ bugs at midnight
  hashedRefreshToken String?             // NULL is meaningful: "no valid session" (logged out)
  ````

  Two small but sharp modeling ideas. (1) **Calendar day ≠ timestamp**: an expiry or a meal date has no
  meaningful time-of-day, and storing one invites timezone bugs (a "Monday" meal showing as Sunday 11pm
  for some users). `@db.Date` stores just the day. (2) **`NULL` can carry meaning**: a nullable
  `hashedRefreshToken` where `null` = "logged out / no session" avoids a second boolean column — the
  presence/absence *is* the state.

  **Where else you'd use it:** birthdays, due dates, holidays → date-only. Nullable-as-state → `deletedAt`
  (null = not deleted), `verifiedAt`, `canceledAt` — a nullable timestamp that doubles as a flag *and*
  records when.

  **Rule of thumb:** use a date type for calendar days (dodge timezone bugs); use a full timestamp only
  when time-of-day matters. Let `NULL` express "absent/none" instead of adding a redundant boolean.

## Queries & Performance

### `select` allow-lists to never leak secret columns
- **What:** `SAFE_USER_SELECT` restricts returned user columns to id/email/name/createdAt — never `passwordHash`/`hashedRefreshToken`; applied in every user read.
- **Where:** `backend/src/modules/users/users.service.ts:14-19`.
- **Why:** Secrets can't accidentally serialize into an API response, even if a handler forgets to strip them.
- **Learn**

  ````ts
  // ❌ returns the WHOLE row, including passwordHash + hashedRefreshToken → one careless handler leaks creds
  return this.prisma.user.findUnique({ where: { id } })

  // ✅ one reusable allow-list, applied everywhere a user is returned
  export const SAFE_USER_SELECT = { id: true, email: true, name: true, createdAt: true } as const
  findSafeById(id: string) {
    return this.prisma.user.findUnique({ where: { id }, select: SAFE_USER_SELECT })
  }
  // Bonus: `Pick<User, keyof typeof SAFE_USER_SELECT>` gives a SafeUser type that CAN'T hold the secrets.
  ````

  Prisma returns every column by default. `select` flips that to an **allow-list**: name exactly the safe
  fields, nothing else comes back. Centralizing it in one constant means "safe to return" is defined once
  and reused, so a new endpoint can't forget and leak a hash. Even better, derive the return *type* from
  it so the compiler enforces the safety.

  **Where else you'd use it:** any table with sensitive columns (users, payment methods, API keys) — one
  shared `select` allow-list as the only way those rows leave the data layer.

  **Rule of thumb:** for tables with secrets, allow-list the safe fields via `select` — don't rely on
  remembering to strip. Forgetting an allow-list omits data (safe); forgetting a block-list leaks it
  (dangerous).

### `include: { recipe: true }` to avoid N+1 in the planner
- **What:** Meal-plan reads pull each entry + its recipe in one query.
- **Where:** `meal-planner.service.ts:37,60`.
- **Why:** Rendering the week grid needs the recipe per entry; a single join beats one query per entry.
- **Learned / Gotcha:** `include` issues an efficient batched query, but `select` and `include` are mutually exclusive at the same level — choosing one shapes the whole result type.
- **Learn**

  **Vocabulary:** *N+1* = the query pattern where you run **1** query for a list, then **N** more (one per
  row) to load each row's relation.

  ````ts
  // ❌ N+1: 1 query for entries, then 1 MORE per entry. 21 meals in a week = 22 round-trips.
  const entries = await prisma.mealPlanEntry.findMany({ where: { userId } })
  for (const e of entries) e.recipe = await prisma.recipe.findUnique({ where: { id: e.recipeId } })  // +1 each!

  // ✅ `include` loads entries AND their recipes together
  const entries = await prisma.mealPlanEntry.findMany({
    where: { userId, date: { gte: start, lte: end } },
    include: { recipe: true },      // each entry comes back with `.recipe` populated
  })
  ````

  Database round-trips dominate performance — 22 tiny queries are far slower than 1–2 batched ones. N+1 is
  the classic ORM trap because the extra queries hide inside an innocent-looking loop. `include` tells
  Prisma to fetch the relation up front.

  **Where else you'd use it:** any list-then-relation access — posts + authors, orders + line items, users
  + roles. If you see a DB query inside a `for`/`map` over rows, that's the N+1 smell — hoist it into an
  `include`/`select` or a single batched query.

  **Rule of thumb:** never query inside a loop over DB rows. Load relations with `include`/nested `select`
  in the original query.

### `deleteMany({ where: { id, userId } })` as an ownership-scoped delete
- **What:** Deletes filter on both id AND userId, then check `count === 0 → 404`, instead of a separate ownership SELECT before delete.
- **Where:** `recipes.service.ts:59`, `shopping:60`, `pantry:78`, `meal-planner:66`.
- **Why:** One query does authorization + deletion; a non-owner's delete simply affects 0 rows.
- **Learned / Gotcha:** `delete` throws P2025 if no row matches; `deleteMany` returns `{ count: 0 }` — so the pattern uses `deleteMany` and inspects the count rather than catching an exception.
- **Learn**

  ````ts
  // ❌ two round-trips AND an auth hole: deletes by id only — user A could delete user B's row
  const found = await prisma.shoppingItem.findFirst({ where: { id } })
  if (!found) throw new NotFoundException()
  await prisma.shoppingItem.delete({ where: { id } })   // ignores owner!

  // ✅ one query that deletes ONLY if this user owns the row; count tells us what happened
  const { count } = await prisma.shoppingItem.deleteMany({ where: { id, userId } })
  if (count === 0) throw new NotFoundException("Shopping item not found.")
  // count 1 → deleted;  count 0 → no such id OR not this user's row (both → 404, no info leak)
  ````

  Folding the owner into the `where` makes the ownership check *part of* the delete — a row that isn't
  yours doesn't match, so it isn't touched. `deleteMany` (not `delete`) matters: `delete` throws `P2025`
  on no-match (forcing try/catch), while `deleteMany` returns `{ count }`, so a plain `if (count === 0)`
  cleanly separates "done" from "nothing to delete." Returning the same 404 for "not found" and "not
  yours" avoids leaking whether the id exists.

  **Where else you'd use it:** every owner-scoped mutation — update/delete a comment, order, file. Put the
  owner in the `where` instead of a separate SELECT-then-check. Use `updateMany`/`deleteMany` when you
  want a count instead of a throw-on-miss.

  **Rule of thumb:** scope owner-restricted writes with `where: { id, ownerId }` — one query, race-free,
  secure by construction. Don't SELECT-then-check.

### `$transaction` for the promote-to-pantry move
- **What:** `promoteToPantry` atomically creates the pantry row and deletes the shopping row.
- **Where:** `shopping.service.ts:72-84`.
- **Why:** The item must never exist in both lists or neither; the two writes must succeed or fail together.
- **Learn**

  **Vocabulary:** a *transaction* groups multiple writes so the DB applies them **all-or-nothing** — if
  any fails, all roll back. *Atomic* = indivisible; observers see either all of it or none.

  ````ts
  // ❌ two independent writes: a crash between them leaves the item in BOTH lists (or lost)
  await prisma.pantryItem.create({ data: { ...item } })
  await prisma.shoppingItem.delete({ where: { id } })   // what if this throws?

  // ✅ both run as ONE atomic unit: all commit, or none do
  await prisma.$transaction([
    prisma.pantryItem.create({ data: { userId, name: item.name, /* … */ } }),
    prisma.shoppingItem.delete({ where: { id } }),
  ])
  ````

  "Promote to pantry" is logically one action made of two writes (add here + remove there). Without a
  transaction, a mid-way failure leaves inconsistent state — duplicated or lost. Wrapping them makes the
  pair indivisible.

  **Where else you'd use it:** money transfer (debit A, credit B), "accept invite" (create membership +
  delete invite), inventory moves, anything that updates 2+ rows that must agree. A single write is
  already atomic and needs no transaction.

  **Rule of thumb:** 2+ writes that must stay consistent with each other → wrap in a transaction. If you
  can describe it as "either both happen or neither," it's a transaction.

### `upsert` for idempotent writes
- **What:** Meal-plan set and preferences save use `upsert`.
- **Where:** `meal-planner.service.ts:56` (keyed on `userId_date_slot`), `preferences.service.ts:23,39`.
- **Why:** "Set the meal for this slot" / "save my prefs" should create-or-update in one call without a pre-check.
- **Learn**

  **Vocabulary:** *idempotent* = doing it once or many times yields the same end state. *upsert* =
  update-or-insert in one statement, decided by a unique key.

  ````ts
  // ❌ check-then-write: two queries, and a race — two requests both see "not found" and both create
  const existing = await prisma.mealPlanEntry.findUnique({ where: { userId_date_slot } })
  if (existing) await prisma.mealPlanEntry.update(/* … */); else await prisma.mealPlanEntry.create(/* … */)

  // ✅ one atomic "create it, or update it if it already exists"
  await prisma.mealPlanEntry.upsert({
    where:  { userId_date_slot: { userId, date, slot } },  // the unique key that decides create vs update
    create: { userId, date, slot, recipeId },
    update: { recipeId },                                   // slot taken → just swap the recipe
  })
  ````

  `upsert` makes the write **idempotent**: "put recipe X in Monday-dinner" reaches the same state whether
  or not the slot was filled, and is safe to retry. The composite unique index `@@unique([userId, date,
  slot])` is what makes the `where` valid — upsert needs a unique target.

  **Where else you'd use it:** settings/preferences ("save"), single-slot assignments, sync jobs
  ("ensure this external record exists locally"), idempotent webhook handlers. Anywhere "set this to
  that, don't care if it existed."

  **Rule of thumb:** for "set" semantics on a uniquely-keyed row, use `upsert` — it's atomic and closes
  the check-then-create race a `findUnique` + branch leaves open.

## Indexing

### Per-user list indexes + composite covering indexes
- **What:** `@@index([userId])` on PantryItem/Recipe/ShoppingItem; composite `@@index([userId, cuisine])` and `@@index([userId, difficulty])` on Recipe; `@@index([userId, date])` on MealPlanEntry for the week-range query.
- **Where:** `schema.prisma:109,137-139,155,172`.
- **Why:** Indexes match the exact query shapes (list-by-user, filter-by-facet, date-window) so those reads stay index-served as data grows.
- **Learn**

  **Vocabulary:** an *index* is a sorted lookup structure the DB keeps so it can find matching rows
  without scanning the whole table. A *composite index* covers multiple columns in order.

  ````prisma
  model Recipe {
    userId String
    @@index([userId])                 // fast "all recipes for this user"
    @@index([userId, cuisine])        // fast "this user's Italian recipes" (filter browsing)
    @@index([userId, difficulty])     // fast "this user's easy recipes"
  }
  // Query the index supports:  where: { userId, cuisine }   → index-served, no full-table scan
  ````

  Without an index, `WHERE userId = ...` scans **every** row (fine at 100 rows, painful at 1M). An index
  makes it a direct lookup. **Composite** column *order* matters: `[userId, cuisine]` accelerates queries
  that filter on `userId` alone *or* `userId + cuisine` (a left-prefix), but not `cuisine` alone. That's
  why each index mirrors a real query the app runs — indexes aren't free (they cost write time + storage),
  so you add them for actual access patterns, not speculatively.

  **Where else you'd use it:** any column you frequently filter, sort, or join on — foreign keys, status
  columns, `createdAt` for time-ordered lists. Match composite indexes to your real `WHERE` clauses,
  most-selective/most-common-prefix first.

  **Rule of thumb:** index the columns your real queries filter/sort on; order composite columns to match
  your `WHERE` prefixes. Don't over-index — every index slows writes.

### Unique constraints
- **What:** `User.email @unique`, `Preference.userId @unique` (1-1), composite `@@unique([userId, date, slot])` on MealPlanEntry (also the `upsert` target).
- **Where:** `schema.prisma:65,83,154`.
- **Why:** DB-enforced invariants (one account per email, one preference row per user, one meal per user/day/slot) rather than app checks that can race.
- **Learn**

  ````prisma
  email  String  @unique                     // DB rejects a duplicate email — atomically, race-free
  @@unique([userId, date, slot])              // at most one meal per user/day/slot; also enables upsert
  ````

  App-level "check if it exists, then insert" has a **race**: two concurrent requests both check "no
  duplicate," both insert, and you get two. A **unique constraint** pushes the guarantee into the DB,
  which enforces it atomically — the second insert fails with `P2002` (which your Prisma exception filter
  maps to 409). Constraints also *enable* `upsert`, whose `where` must target a unique key.

  **Where else you'd use it:** emails/usernames, one-row-per-parent (1-1) relations, "one vote per
  user per poll," slugs. Any "there can only be one of these" rule belongs as a DB constraint.

  **Rule of thumb:** enforce uniqueness in the DB with a `@unique`/`@@unique`, not with an app-level
  existence check — only the DB can do it without a race.
